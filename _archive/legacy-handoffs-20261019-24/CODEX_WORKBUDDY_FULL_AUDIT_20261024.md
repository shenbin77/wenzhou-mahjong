# WorkBuddy 全面开发只读审计（2026-10-24）

## 结论

当前版本可继续作为**只读推荐与采集工具**开发，**不能开启全自动点击，也不能宣称财神、动作按钮、牌河或整间代打已验收**。

测试全绿不代表实战正确。本次已发现多处“测试把错误行为固定为正确”的情况，最严重的是杠的数学模型、未知来牌仍可执行动作、点击后验证假通过，以及弃权帧跳过换局和财神更新。

审计是 WorkBuddy 并发施工期间的只读快照。涉及文件最后写入时间截至 2026-10-24 15:32；WorkBuddy 后续修改后必须按本文验收项重新复审。

## P0：必须先修，修完前保持 dry_run

### 1. 副露与杠的向听数学错误

当前子仓库改动把杠的第 4 张称为“余牌”，并再次放进暗手分解，允许它和暗手 2、3 万组成 123 万：

- `代打BOT/majiang-bot/brain_v0/engine/tea/shanten.py:423-442`
- `代打BOT/majiang-bot/brain_v0/tests/test_tea_meld_shanten.py:109-131`

这是错误规则。杠的四张全部已被杠消耗，第 4 张不能再次参与顺子、对子或财神分配。杠只在逻辑牌型中占一个面子；补牌使暗手张数仍按“每组副露减少 3 张”计算：一组副露时，等待态暗手 13 张，摸牌态暗手 14 张。杠的第 4 张只进入物理可见牌计数。

必须整改：

1. 删除 `spares` 回灌暗手分解的逻辑和对应错误测试。
2. 所有模块统一两套计数：`logical_slot_count` 与 `visible_physical_count`。
3. 向听、胡牌、进张、弃牌、`turn_gate`、`action_policy`、`recorder` 使用同一契约。
4. 增加碰、明杠、暗杠、加杠、杠后补牌的人工规则金标测试。

### 2. 动作策略会在证据不足时变成 executable

- `action_policy.py:907`：`incoming_source=None` 会被放行；未知来源可能被当成可碰来牌。
- `action_policy.py:783,1271`：生产默认不要求按钮字形模板；无模板时仍可通过引擎推断选择金色按钮。
- `action_policy.py:1402-1495`：缺字段时跳过检查，胡、过、碰存在点击后假通过。
- `action_policy.py:926`：有副露时直接拒绝胡。
- `action_policy.py:975`：硬编码 2 人局不能吃，与现有茶 2 实战按钮证据冲突。

必须整改：

1. 别人出牌触发的吃、碰、明杠、接炮胡要求 `incoming_source == opponent` 且来源座位合法；未知一律弃权。
2. 自摸胡、暗杠、加杠、杠后补牌与别人出牌事件分开建状态机。
3. 生产自动模式强制真实按钮模板、玩法、来源、画面新鲜度、倒计时和点击通道全部通过。
4. 点后验证必需字段缺一即失败；按钮消失不能单独证明胡或过成功。

### 3. 出牌点击门禁和两击验证不安全

- `turn_gate.py:421-515` 没有读取行动方向灯和倒计时；实机已有倒计时只剩 1 秒仍放行的证据。
- `tap_executor.py:467-525` 第一击后只看像素变化，没有确认牌仍在手中且真正抬起；第一击已出牌时仍可能再点第二次。
- 合成 `tap_probe` 中 `raised=[]` 仍被标记为 `verified`，不能作为实机成功证据。

必须整改：

1. 行动方向灯为主门禁；倒计时不足以覆盖最坏执行延迟时弃权。
2. 每次新截图后重新执行全部门禁。
3. 第一击后若手牌已少一张，判定已出牌并禁止第二击；否则必须确认目标牌仍存在、数量不变且几何上抬。
4. 实机验收只接受 before/selected/after 哈希不同的真实证据。

### 4. 财神模板证据链可被自动候选污染

指定 10:48 原帧的财神确实是七条 `s7`，当前标签无需改名；但 WorkBuddy 的 `0.99998/1.0000` 是“来源裁图匹配来源截图”的同源自匹配。排除该模板后只有 `0.91247`，低于当前 `0.98` 安全阈值，不能宣称泛化通过。

- `caishen_collector.py:188-224` 把模型 top1 直接写成候选标签。
- `review_caishen_pending.py:87-110` 只校验标签合法性，并统一伪写成 `manual_pick reviewed / operator read by eye`。
- `test_caishen_coverage.py:198` 允许随机噪声指定标签后直接入库。
- 当前茶 2 口径：32 种需求，仅 13 种有 timestamp 形式 live 模板，19 种仍缺 live 变体。

必须整改：

1. 自动流程只保存无标签候选与 top-k 提示，不得把预测当真值。
2. 生产入库记录真实 `source_kind/review_method/reviewer/source_frame_hash/heldout_passed`。
3. 必须用第二张独立实战帧验证；增加 leave-one-source-out 测试。
4. “来源帧自匹配”只能写来源回放通过，不能写准确率或实战可用。

### 5. 实时主链路与全自动生命周期未完成

- `assist_window.py:659` 在 `abstain` 时提前返回，跳过 671 行后的换局和财神检查；新局首帧不完整时可能保留上一局手选财神。
- 自动发现换局只更新内部指纹，不同步真实局数、记录器、牌河基线和历史。
- `auto_play_loop.py:382` 先处理动作按钮并提前返回，策略使用上一帧 `_last_result`。
- `CLAIM_TAP_CHANNEL_READY=False`，吃碰杠胡过目前只记录，不点击。
- CLI 未接房卡识别器，没有 16 局整间停止，没有未知弹窗停机，没有统一录像和动作台账。

必须整改：

1. 每帧先处理玩法、HUD、换局、财神和当前手牌，再处理建议或动作按钮；`abstain` 只撤销建议。
2. 自动换局同步真实局号、记录器轮次、财神、当前牌河与追加式出牌历史。
3. 完成房卡、16 局结束、结算、邀请/充值/未知弹窗停机和统一证据台账。
4. 在真实按钮金标与点后验证完成前，不得把 `CLAIM_TAP_CHANNEL_READY` 改为 `True`。

## P1：前端和识别完整性

1. 尚无统一 `table_state.py`；`DisplayState` 不含房号、真实局数、庄家/座次、行动方、倒计时、余牌、最近出牌和完整牌河。
2. UI 中房号仍需人工输入，局数是内部计数；`wait` 被无证据解释成“等待摸牌/当前不是出牌回合”。未知必须显示“未识别”。
3. 牌河会静默跳过低分牌却仍可能保持 `valid=True`。应输出 `physical_count/recognized_count/is_complete`，不完整牌河不能用于剩余牌或完整历史。
4. `claim_vision` 目前主要识别通用金色圆盘；测试是程序绘制圆形，没有真实吃碰杠胡过取消字形金标。
5. 当前窗口把“只读、不会代点”和“允许代点”放在同一模式中。主界面应只有互斥的“推荐模式”和“自动代打模式”，半自动探针移入开发设置。
